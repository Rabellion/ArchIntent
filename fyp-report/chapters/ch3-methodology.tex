\section{DEVELOPMENT APPROACH}
\label{sec:dev-approach}
% ---------------------------------------------------------------------
%  CARRIED OVER FROM PROPOSAL SECTIONS 4.1 and 4.3.
% ---------------------------------------------------------------------

This project follows the \textbf{Incremental Model}, in which the system
is developed and delivered in multiple functional increments. Each
increment adds features to, and improves upon, the previous version.
This approach permits early testing, easier debugging, and faster
delivery of working modules \cite{pan2021roles}.

The model suits this project specifically because the AI module carries
the highest technical risk and the least certain requirements. Building
a core functional system first -- registration, login and basic design
browsing -- allowed the platform to be tested end to end before the
speech recognition and semantic matching components were introduced, so
that failures in those components could be isolated from failures in the
surrounding application.

The system is decomposed into five modules, which are carried forward
into the subsystem architecture in Section~\ref{subsec:arch-subsystem}:

\begin{itemize}[leftmargin=*, itemsep=2pt]
  \item \textbf{User Module} -- user registration, authentication,
        browsing of architectural designs, and initiating contact with
        architects.
  \item \textbf{Architect Module} -- design uploads, portfolio
        management, and direct communication with clients using semantic

  \item \textbf{Construction Module} -- allows construction companies to

  \item \textbf{Admin Module} -- administrative control for user

  \item \textbf{AI Module} -- a separate FastAPI service implementing

        voice queries \cite{radford2022whisper}, SpaCy-based keyword
        extraction, and Sentence-BERT embedding with cosine-similarity
        ranking against architect portfolios
        \cite{reimers2019sbert}.
\end{itemize}

The AI Module is a three-stage pipeline, run entirely within the
standalone FastAPI service introduced in
Section~\ref{subsec:major-modules}: speech-to-text
(Section~\ref{subsec:voice-transcription}), keyword
extraction (Section~\ref{subsec:keyword-extraction}), and semantic
matching (Sections~\ref{subsec:text-representation}
--\ref{subsec:similarity-scoring}). Each stage is optional in the sense
that matching works from typed text alone -- voice input is an
alternative way of producing that text, and keyword extraction enriches
it -- but all three are implemented, not just the final matching stage.

\subsection{Voice transcription}
\label{subsec:voice-transcription}

A client may describe their project brief by voice instead of typing
it. The recorded audio is transcribed by the OpenAI-hosted Whisper API
\cite{radford2022whisper} rather than by a Whisper model loaded
in-process. This is a deliberate infrastructure decision, not a
simplification of the technique: the NLP service already loads a
Sentence-BERT model into a memory-constrained deployment
(Section~\ref{sec:tools}), and loading a second transformer model for
speech recognition in the same process would risk the service running
out of memory under real usage. Delegating transcription to a hosted
API removes that failure mode entirely, at a marginal per-request cost.
The returned transcript is inserted into the same brief-text field a
typed submission would use, so every later pipeline stage is identical
regardless of how the brief was produced, and the client can review and
edit the transcript before submitting.

\subsection{Keyword extraction}
\label{subsec:keyword-extraction}

Before a brief is embedded, it is passed through a SpaCy-based
extraction stage that decodes it into four structured categories: style,
room type, material and feature. This is implemented with two
complementary techniques. A \texttt{PhraseMatcher} loaded with a curated
architecture-domain vocabulary catches known multi-word terms as a
single unit (\emph{"open plan"}, \emph{"natural light"}) rather than as
unrelated individual words. A fallback pass over SpaCy's noun-chunk and
adjective annotations catches descriptive terms outside that curated
vocabulary, with overlap filtering so that a chunk already covered by a
matched vocabulary term (\emph{"a rooftop terrace"} once
\emph{"terrace"} is matched) is not repeated.

The extracted terms serve two purposes. They are appended to the brief
before it is embedded (Section~\ref{subsec:text-representation}),
increasing their weight in the resulting vector relative to surrounding
filler words. They are also returned directly to the client through a
dedicated endpoint, independent of matching, so the interface can show a
"we understood: modern, minimalist, open-plan" confirmation while the
brief is still being written -- a visible, checkable instance of the
intent-decoding claim central to this project, rather than a step that
only affects an internal score the client never sees.

\subsection{Text representation}
\label{subsec:text-representation}

Two text representations are constructed. A \emph{project text} is
assembled from the project type, the location and the client's written
brief, then enriched with the keywords decoded in
Section~\ref{subsec:keyword-extraction} before embedding. An
\emph{architect text} is assembled from the architect's specialisation
and biography, concatenated with the description and style tags of one
of their portfolio projects.

Crucially, one architect text is built for \emph{each} portfolio project
an architect owns, rather than one per architect. This lets the system
score an architect by their single best-matching work instead of by an
average over an uneven portfolio, or by whichever project happened to be
uploaded first. An architect with no portfolio projects is still
represented, by their base specialisation and biography text alone.

\subsection{Similarity scoring}
\label{subsec:similarity-scoring}

All texts -- the project text and every architect-project text -- are
encoded in a single batch using a Sentence-BERT model, by default
\texttt{all-MiniLM-L6-v2}, with the embeddings L2-normalised at encoding
time. Cosine similarity is then computed between the project vector and
every candidate vector.

\subsection{Integration with the main application}
\label{subsec:nlp-integration}

The Laravel application and the FastAPI service communicate over three
endpoints, all authenticated by a shared key sent as an
\texttt{X-Internal-Key} header so the NLP service cannot be called by
an unauthenticated party.

\begin{itemize}[leftmargin=*, itemsep=2pt]
  \item \texttt{POST /transcribe} -- called when a client submits a
        voice recording. The audio is streamed through to the OpenAI
        Whisper API and the resulting transcript is returned; nothing is
        persisted at this stage.
  \item \texttt{POST /extract-keywords} -- called live, while a client
        is writing or reviewing their brief, before a project exists.
        Returns the structured terms described in
        Section~\ref{subsec:keyword-extraction} for the frontend
        confirmation chips.
  \item \texttt{POST /match} -- called asynchronously after a project is
        created, via a queued job. This is the only one of the three
        that writes to the database: the returned ranked list is
        persisted to the \texttt{project\_matches} table, and this
        endpoint performs its own keyword extraction and enrichment
        internally, so matching quality does not depend on whether the
        client's brief was previewed through
        \texttt{/extract-keywords} beforehand.
\end{itemize}
